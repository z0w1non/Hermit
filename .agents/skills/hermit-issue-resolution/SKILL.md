# Hermit 課題解決

## 目的

プロジェクト全体を対象に、課題を根拠付きで洗い出し、改善案を選択して実装し、Release x64 のビルドと単体テストで検証し、コードと資料の整合を確認する。単一ファイルの変更で終了せず、完了条件を満たすまで反復する。

## 適用範囲と前提

- `AGENTS.md`、`docs/REQUIREMENTS.md`、`docs/ISSUES.md`、`docs/SPECIFICATION.md`、`readme.md`、`.vcxproj`、`Hermit/`、`test/`、`.agents/skills/` を調査対象とする。
- `third_party/` と `vcpkg_installed/` は作業対象・検索対象・検証対象から除外する。
- 生成物やローカル環境設定を理由なく変更・コミットしない。
- Windows、MSVC、C++20、vcpkg manifest、Google Test を前提とし、AGENTS.md の Google C++ Style Guide 命名規則、CLI/INI の kebab-case、書式、Windows ヘッダー汚染防止方針に従う。

## 一連の流れ

### 1. 課題を洗い出す

1. `AGENTS.md` と関連スキルを読み、現在の方針・除外範囲・検証条件を確認する。
2. `docs/REQUIREMENTS.md` の宣言的要求と `docs/ISSUES.md` の既知課題を読み、要求から作業計画を組み立てる。ユーザーの明示的指示なしに要求本文を作成・変更しない。
3. `docs/SPECIFICATION.md`、`readme.md`、ソース、プロジェクト設定、テストを照合する。
4. ビルドログ、テスト結果、公開 API、CLI オプション、ヘッダー依存、TODO、未検証の外部境界を根拠として課題候補を列挙する。
5. 各候補を次のいずれかに分類する。
   - **課題**: 現在の不具合、欠落、再現可能な不整合、または品質上の明確な不足。
   - **検討事項**: 現時点では不具合と断定できないが、改善効果や設計判断を評価する事項。
6. 確定課題と検討事項を分ける。課題の追加・状態変更・解決記録は `docs/ISSUES.md` に記録し、`docs/SPECIFICATION.md` の課題表には優先度順の要約と参照を保つ。後続作業の前提となる依存性注入境界を先に扱い、注入不能が単体テストを妨げる課題は優先度「高」とする。

### 2. 解決計画を立てる

- 作業開始時に `docs/REQUIREMENTS.md` の要求を目的・受け入れ条件として読み、`docs/ISSUES.md` の未解決課題の優先度、既存の根拠、解決策候補、前回までの試行結果を依存順の計画へ反映する。新しい課題だけを優先して既存課題を置き去りにしない。
- 要求と課題または実装に矛盾があれば、要求本文を自己判断で直さず、矛盾を記録して独立して進められる作業を進める。要求の意味や受け入れ条件を左右する判断はユーザーへ確認する。
- 影響度、再現性、ビルド・テストへの影響、変更範囲、依存関係を比較して着手順を決める。注入不能な外部境界を先に解消し、その後に境界を利用する単体テスト不足を解消する。
- 対象となる `.cpp`、最小の公開ヘッダー、テスト、プロジェクト設定、資料を対応付ける。
- 外部サービスや OS・ネットワーク・ファイルシステム境界は、可能ならテンプレートパラメータ等で依存性注入し、Google Test Mock で決定的に検証できる設計を優先する。
- 完了条件を「実装済み」だけにせず、再現テスト、Release x64 ビルド、単体テスト、資料同期まで定義する。

### 3. 実装する

- 責務を持つ最小のファイルを変更し、各 `.cpp` は対応する最小ヘッダーだけを参照する。巨大な集約ヘッダーへの依存を新たに増やさない。
- 公開境界、AST・文法・評価、設定型、バックエンド、テンプレート実体を必要な単位に分離する。
- 追加・変更したソースは `.vcxproj` とソリューション構成へ反映する。
- Windows API を使わないソースに `Windows.h` を追加しない。使う場合だけ `WIN32_LEAN_AND_MEAN`、`STRICT`、`NOMINMAX` を必要に応じて定義し、汎用マクロを undef する。
- `third_party/`、`vcpkg_installed/` の内容には触れず、依存関係の修正は manifest、プロジェクト設定、利用側コードで行う。

### 4. テストを追加・更新する

- 公開関数・クラスの正常系、境界値、失敗系、設定既定値、エラー伝播を対象に不足を洗い出す。
- 注入可能になった外部境界には Mock を追加し、ネットワーク、プロセス、実サービスに依存しない決定的な単体テストを優先する。
- 既存テストが新しい公開境界や依存性注入方式と一致しない場合は、旧テストを残して水増しせず、責務に合う形へ変更する。
- 課題の再現テストを先に追加できる場合は、失敗を確認してから修正し、修正後に同じテストが通ることを確認する。

### 5. ビルド・実行で検証する

- Release x64 の差分ビルドと全テストを実行する。PTY、セッション保持、PDB・loopback 制約、診断と終了コードの確認は `hermit-build-test` を正本として使う。
- 実行できない場合は理由と確認した事実を記録し、成功と推測しない。

### 6. 資料を同期する

- ファイル構成、公開 API、責務、ヘッダー依存、ビルド構成、テスト構成を変更したら、同じ変更単位で `docs/SPECIFICATION.md` を更新する。
- 公開 CLI オプション、設定、実行方法、入出力を変更したら `readme.md` も更新する。実装の詳細なマクロ仕様や内部依存の説明は仕様書に置き、README と重複させない。
- vcpkg の依存関係や復元方法を変更したら、`vcpkg.json`、`vcpkg-configuration.json`、README、仕様書を照合する。
- 開発方針や検証手順を変更したら `AGENTS.md` と関連スキルを同じ変更単位で更新する。
- ユーザー承認済み要求の正本は `docs/REQUIREMENTS.md` とする。要求そのものはユーザーが直接記載するか、更新を明示的に指示した場合のみ変更し、実装発見や改善提案は `docs/ISSUES.md` 等へ記録する。
- 見出しを追加・変更した場合は、資料全体の見出し階層と表の参照関係を再確認する。

### 7. 解決を判定し記録する

課題を解決済みとする条件は、次のすべてを満たすことである。

1. 根本原因に対応する実装が完了している。
2. 失敗を再現するテスト、または不足を補う回帰テストがある。
3. Release x64 の差分ビルドが成功している。
4. `test.exe` が成功し、結果を確認できる。
5. コード、プロジェクト設定、README、仕様書、AGENTS.md、関連スキルの記述が一致している。
6. `docs/ISSUES.md` で状態を「解決済み」にし、解決内容・検証結果を残している。`docs/SPECIFICATION.md` の課題表も同期し、解決済み課題は削除しない。

原因が特定できない、ビルドが再現不能、または外部要因で検証できない場合は、解決済みとせず、課題表の状態を維持または更新し、確認済みの事実、試した改善案、阻害要因、次の選択肢を記録して停止する。

作業を阻害する要因を見つけた場合は、課題台帳または該当する技術資料へ確認した証拠・影響・対処履歴・次アクションを記録する。解消できた場合も、阻害内容と解決策・検証結果を同じ記録へ残す。推測を確定原因として記載しない。

## 反復と停止条件

一つのファイルを直して終了せず、変更後にもう一度プロジェクト全体を走査する。各反復の開始時に課題表を再読し、未解決課題を優先度順に再評価する。次のいずれかになるまで、課題の追加、実装、テスト、資料同期、検証を反復する。

- actionable な課題がなくなり、仕様書・README・設定・コード・テストの不整合がない。
- 残る事項が検討事項のみで、現時点の変更に明確な利点がない。
- 同一の根本原因に対する安全な改善案を尽くしても、外部状態の変更やユーザー判断なしには進められない。その場合は阻害理由を記録して停止する。

完了報告には、解決した課題、変更したファイル、検証コマンドと結果、未解決項目があればその理由を含める。
